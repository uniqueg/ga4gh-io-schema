# Roadmap

## Next steps

To drive adoption and prove out the utility of the IO Schema Profile, we propose the following immediate next steps:

1. **Schema Translation Tooling:** Develop lightweight, open-source translation scripts to convert existing `nextflow_schema.json` and CWL `CommandLineTool` inputs into compliant GA4GH IO Profile schemas.

2. **End-to-End Proof of Concept (PoC):** Construct a sandbox environment featuring a mock TRS registry hosting IO schemas (as `ga4gh-io.schema.json` files, see [TRS](adoption/trs.md)), a generic frontend (e.g., via `react-jsonschema-form`) rendering input forms and compiling WES requests, and a proxy WES gateway enforcing server-side validation against the schema prior to execution.

3. **Formal Specification Submission:** Following the PoC, submit the IDL schema structure, the `x-ga4gh-*` vocabulary, and the proposed API modifications to the GA4GH [Federated Analysis Work Stream](https://www.ga4gh.org/work_stream/federated-analysis-work-stream-formerly-cloud-work-stream/) (formerly the Cloud Work Stream, which develops TRS, WES, DRS and TES) for formal standardization review.

## Scope of version 0.3

Version 0.3 narrows the profile to its core use: input forms, run requests
and outputs. Earlier versions of the proposal contained features that add
risk without serving that use. They are either cut (removed, with no plan to
bring them back) or deferred (removed or kept experimental until a later
version specifies them properly). See
[#17](https://github.com/uniqueg/ga4gh-io-schema/issues/17); the changelog
of the repository lists each removal as a breaking change.

### Cut

| Feature | Reason |
| ----- | ----- |
| The claim that the profile is domain-agnostic and suits machine learning pipelines (MLOps); a claim, not a feature | The profile is not designed or tested for it; whether it could be is an [open question](#open-questions). |
| `x-ga4gh-fa-icon` (FontAwesome icon class) | Ties schemas to one icon library and one kind of client; icons are a portal's choice, not part of the contract. The meta-schema rejects the keyword. |
| `rst` as a value of `x-ga4gh-description-format` | reStructuredText has directives that embed raw HTML or include files, so it can't be rendered safely in a browser (see [Rendering schemas and outputs](security.md#rendering-schemas-and-outputs)); `markdown` covers formatted descriptions. |
| IO schemas supplied by clients in a run request | A server would validate the request against a schema that the requester chose; schemas come from trusted sources only (see [Sources of schemas](security.md#sources-of-schemas)). |
| Drafting of IO schemas by AI agents (reference implementation and adoption path) | A drafted schema is a guess about a workflow's interface; schemas belong to the workflow and are published with it (by its authors, or generated by [converters](tools/converters.md) from the workflow's own declarations). |
| The `password` widget | Workflow parameters are not a channel for secrets (see [Secrets](security.md#secrets)). |

### Deferred

| Feature | Reason | Until then |
| ----- | ----- | ----- |
| Chaining workflows by ontology terms (which outputs fit which inputs) | Needs matching rules (e.g., for more specific terms, genome builds, compression, format versions) that the profile doesn't define (see [APE and Workflomics](related-work.md#ape-and-workflomics)). | `x-ga4gh-ontology` annotates inputs and outputs; matching is up to clients. |
| Viewers other than download, tables and sandboxed HTML: `genome-browser`, `scatter-plot`, `pdf-viewer`, `markdown-viewer` | Each viewer needs its own rendering and security rules (e.g., PDF and Markdown can carry active content or load external resources). | The vocabulary has `table-viewer` and `html-viewer`; outputs without a known viewer are offered for download. The rendering rules apply by content, so a `custom:` widget doesn't lift them (see [Rendering schemas and outputs](security.md#rendering-schemas-and-outputs)). |
| Validation of tabular files (e.g., sample sheets) against `x-ga4gh-tabular-schema` | Needs the rules that [Frictionless Table Schema](related-work.md#frictionless-table-schema) and Table Dialect already define (typed cells, empty cells, dialects), and makes the server a data accessor (see [Validation of data files on the server](security.md#validation-of-data-files-on-the-server)). A later version may adopt Table Schema by reference. | `x-ga4gh-tabular-schema` is kept as an experimental form hint (e.g., for a spreadsheet editor), not a validation rule. |
| A TRS file type `IO_SCHEMA` (and a field naming the schema standard of a file) | Needs a change to TRS. | IO schemas are published with the existing file type `OTHER` and the path `ga4gh-io.schema.json` (see [TRS](adoption/trs.md#publishing-convention)). |

## Open questions

- **Does the profile suit machine learning models and pipelines (MLOps)?**
  Earlier versions of this proposal claimed that the profile is
  domain-agnostic and suits machine learning pipelines as well as genomic
  workflows. Version 0.3 drops that claim: the profile is designed and tested
  for workflows in the life sciences only. Whether it also fits, e.g.,
  hyperparameters of training pipelines and model artefacts as outputs, and
  how it would relate to dataset descriptions such as
  [Croissant](https://docs.mlcommons.org/croissant/docs/croissant-spec-1.1.html),
  is open. The GA4GH
  [AI Work Stream](https://www.ga4gh.org/news_item/ga4gh-launches-new-work-stream-to-support-responsible-ai-in-genomics-and-health/)
  would be the place to discuss it.
