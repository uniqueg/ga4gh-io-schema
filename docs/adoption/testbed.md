# Testbed

The live demo of the profile is the [prototype](prototype.md) of this
repository: a TRS stub that serves the demo workflow, the host of a generic
form, and the WES run request that the form builds. Everything it needs is
in the repository, and it runs on one laptop. It is a proof of concept, not
an implementation within a real stack, and it is self-contained: anybody
who checks out the repository can run it on their own, without tokens,
accounts or deployed services.

This page describes the testbed as a whole: how to run it, its parts, what
is real and what is mocked, and its limits. The
[prototype](prototype.md#walkthrough) page walks through the demo step by
step, and the [evaluation](prototype-evaluation.md) says what it showed
about the profile.

## Run it

**Prerequisites:**

- Git, and Docker with Docker Compose v2 (`docker compose`). CI runs the
  stack on GitHub's `ubuntu-latest` runner (the `ubuntu-26.04` image in
  November 2026), with the Docker Engine and Compose that it ships; any
  recent Docker with Compose v2 should do.
- Ports `8000` and `8080` free on `127.0.0.1`.
- A web browser.
- Network access for the first build: it pulls `python:3.13-alpine` and
  installs this package from the checkout, with its dependencies from
  PyPI. Once the image is
  built, the stack runs offline.

**Steps,** from any directory:

1. Clone the repository and enter it:

    ```bash
    git clone https://github.com/elixir-cloud-aai/ga4gh-io-schema.git
    cd ga4gh-io-schema
    ```

2. Build the image and start the stack (the first build takes a minute or
   two). `env -u` makes sure that `TRS_URL` and `WES_URL` of your shell, if
   set, don't point the stack at another TRS or WES (see [Point it at a
   real TRS or WES](prototype.md#point-it-at-a-real-trs-or-wes)):

    ```bash
    env -u TRS_URL -u WES_URL docker compose -f prototype/compose.yaml up --build
    ```

    Compose prints the logs of the two services, `trs-stub` and `host`; the
    host starts once the stub is healthy.

    If a port is in use (e.g., port 8080 by a local TRS-Filer or a port
    forward), Compose stops with `address already in use`. Free the port,
    or publish the service on another port with an override file in a
    temporary location, outside the checkout (Compose 2.24 or later, for
    `!override`), e.g., for the stub:

    ```bash
    override=$(mktemp)
    printf 'services:\n  trs-stub:\n    ports: !override\n      - "127.0.0.1:18080:8080"\n' > "$override"
    env -u TRS_URL -u WES_URL docker compose -f prototype/compose.yaml -f "$override" up --build
    ```

    The host reaches the stub inside the stack, so the demo doesn't change;
    only `curl` calls to the stub from your machine use the new port. For
    the host, override `ports` of the service `host` the same way and open
    the page on that port. Step 4 works as it is; remove the file
    afterwards with `rm "$override"`.

3. Open <http://127.0.0.1:8000/>, pick "I/O Schema demo 1.0.0 (WDL)" and
   follow the [walkthrough](prototype.md#walkthrough): a mapping quality of
   61 gives the schema's error message, 20 with `proper_pairs` gives the
   run request.

4. Stop the stack with `Ctrl+C`, then remove its containers and network,
   and the image:

    ```bash
    docker compose -f prototype/compose.yaml down --rmi all
    ```

## The parts

| Part | Where | What it does | Real or mocked |
| --- | --- | --- | --- |
| Profile | `schemas/` | The meta-schema and vocabularies that the IO schema is validated against. | Real: the schemas of version 0.3.0. |
| Demo workflow | `examples/demo/demo.wdl` | A WDL 1.1 workflow that filters, sorts and indexes aligned reads and writes a report. | Real, but never run by the testbed. |
| IO schema | `examples/demo/ga4gh-io.schema.json` | The inputs and outputs of the workflow, generated by `build_schema.py` from the output of [`convert wdl`](../tools/convert-wdl.md) and `schema.overlay.json`. | Real. |
| TRS stub | `prototype/trs-stub/trs_stub.py`, service `trs-stub` | Serves the tool `ga4gh-io-schema-demo`, version `1.0.0`, descriptor type `WDL`, with two files from `examples/demo/`: the primary descriptor `demo.wdl` and the IO schema `ga4gh-io.schema.json` (type `OTHER`, by the [publishing convention](trs.md#publishing-convention)). | Mocked: a few read endpoints of TRS v2, not a TRS implementation (see [TRS stub](prototype.md#trs-stub)). |
| Form host | `prototype/host/`, service `host` | Lists the workflows of a TRS (`--trs-url`), finds and fetches the IO schema of the one picked, validates it against the profile, checks its workflow block (ids, descriptor type, checksum of the primary descriptor; see [workflow block check](../tools/verify.md)), renders the form, reports wrong values with the schema's messages, and builds the WES run request. | Real: the validator, the workflow block check and the request builder of the `ga4gh-io-schema` package, and the [form proof of concept](form.md) of this repository. |
| WES run request | Shown under the form | `workflow_params` from the engine binding for WDL (names qualified with the workflow name), `workflow_type` and `workflow_type_version` from the workflow block, and the TRS URL of the plain primary descriptor as `workflow_url`. | Real, but not sent. |
| WES | Not part of the testbed | With `WES_URL` set, the host offers "Send to WES" and posts the request to `POST /runs`; without it, nothing is sent, and the page says so. | Absent. |

The run request for the values of the walkthrough:

```json
{
  "workflow_params": {
    "io_schema_demo.reads": "https://raw.githubusercontent.com/nf-core/test-datasets/3e548a3b34994380db1602506e0721fadbad6de1/data/genomics/sarscov2/illumina/bam/test.paired_end.bam",
    "io_schema_demo.min_mapq": 20,
    "io_schema_demo.read_filter": "proper_pairs"
  },
  "workflow_type": "WDL",
  "workflow_type_version": "1.1",
  "workflow_url": "http://trs-stub:8080/ga4gh/trs/v2/tools/ga4gh-io-schema-demo/versions/1.0.0/PLAIN_WDL/descriptor/demo.wdl"
}
```

## Real and mocked

- **Real:** the profile, its schemas, the validator, the converters (which
  produced the IO schema), the workflow block check, the request builder,
  and the form. They are the same code that the package and its tests use.
- **Mocked:** the TRS. The stub implements the few read endpoints that a
  client needs to find a workflow and its IO schema, and nothing else (no
  writes, no service info, no paging).
- **Absent:** a WES, a workflow run and its outputs. The testbed stops at
  the run request. The run log in `examples/demo/expected/run-log.json`
  isn't a recorded run: it is written from the source code of a WES
  implementation, for the tests of the [output
  normaliser](../tools/outputs.md).

## Limits

- **No authentication, no TLS, no deployed services:** the ports are bound
  to `127.0.0.1`, and the TRS is a stub. The demo says nothing about how
  the profile works with access control or with real registries.
- **One demo workflow, one language:** WDL only, one file. The bindings for
  CWL, Nextflow and Snakemake are tested in the package, not in the
  testbed.
- **No runs:** the testbed shows that an IO schema is enough to get from a
  workflow in TRS to a valid WES run request, not that a WES runs it or
  that the outputs fit the schema.

For the conclusions, this means: they hold for discovering, checking and
rendering an IO schema and for building run requests; they are not
evidence for execution, outputs, security in deployment or other
languages (see [Limits of the
prototype](prototype-evaluation.md#limits-of-the-prototype)).

## How it is tested

CI's job "End-to-end test" runs the same stack from a fresh checkout
(`docker compose -f prototype/compose.yaml up --detach --build --wait`) and
`tests/test_prototype_e2e.py`, which takes the path of the walkthrough over
the host's HTTP API and in a browser (Chromium, driven by Playwright): the
list of workflows, the IO schema, the error message for a mapping quality
of 61 and the run request above. To run it locally, see [Test
it](prototype.md#test-it).

A demo of the profile with deployed services, e.g., the components of a
platform, is out of scope here; the [end-to-end demo](demo.md) is a guide
for adopters, not part of the testbed.
